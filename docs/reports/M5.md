Probed and found **already sound** (kept as regression tests): other organisations' consents and statements answer identically to nonexistent ones and cannot be changed; duplicate/trailing-junk bearer tokens and tokens used with another certificate of the same organisation are refused; responses contain exactly the documented properties; server-controlled properties cannot be mass-assigned; oversized, deeply nested, huge-array and `1e999` bodies and slow headers are refused cheaply; method-override headers, TRACE/OPTIONS/PUT/DELETE/PATCH and path tricks reach nothing; a scope-limited client cannot gain scopes at the token endpoint; consent is checked for the exact number, purpose and signal and revocation is immediate; no participant value becomes an outbound URL, host or header; every response (including errors and 404) carries the hardening headers and no fingerprint, CORS or cookie; CL.TE smuggling and obsolete line folding are rejected; error bodies leak nothing; every registered route is in the OpenAPI document and vice versa; hostile telco answers never produce FALSE.

## Branch protection (H-001), observed
You said branch protection is on. At 22:5x UTC on 2026-11-27 the GitHub API showed: no classic protection on `main` (HTTP 404 "Branch not protected"); one repository ruleset, `Standard` (created 21:51), with **enforcement `disabled`**, **no target branches** (`include` empty), and rules for deletion, non_fast_forward, creation, update and required_signatures but **no pull-request rule and no required status check**. As configured it protects nothing. To make `gate` required: set the ruleset's enforcement to Active, target `main` (default branch), and add "Require status checks to pass" with the `gate` check and "Require a pull request before merging". Note the `update` rule blocks every push to a targeted branch and `required_signatures` needs signed commits (squash merges made on github.com are signed by GitHub; commits pushed from this environment are not). Re-check performed again at the end of M5 is recorded below.

## Neon
You have a Neon database connected to the `telcosignal` Vercel project: the project's production environment holds the integration's variables (names only are visible to me; the values are sensitive and neither the Vercel API nor GitHub's secrets API lets me read them). The GitHub secret names are not listable from this session either, so I added a manual workflow, `.github/workflows/neon-verify.yml` + `scripts/neon-verify.mjs`, that tries the usual secret names (`DATABASE_URL_UNPOOLED`, `POSTGRES_URL_NON_POOLING`, `NEON_DATABASE_URL`, `DATABASE_URL`, `POSTGRES_URL`), insists on a direct `*.neon.tech` host, never prints the URL, creates only `ts_*` roles and `ts_t_*` databases and runs the whole test suite against it with synthetic data. Result of the run: see the addendum at the end of this report.
